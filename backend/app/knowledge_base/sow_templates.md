# Statement of Work (SOW) Templates and Section Guidance

## Standard SOW Structure
A professional Statement of Work for a services engagement should always contain the
following sections, in order: Project Overview, Scope of Work, Deliverables, Timeline
and Milestones, Assumptions, and Commercials. Each section has a distinct purpose and a
distinct audience.

## Project Overview Guidance
The Project Overview states the client name, the business context, and the primary
objectives in two to four sentences. It should describe the "why" of the engagement in
business language, not technical jargon. A strong overview names the client's industry,
the type of initiative (for example cloud migration or application modernization), and
the headline outcome the client expects. Avoid listing tasks here; the overview is about
outcomes and value.

## Scope of Work Guidance
The Scope of Work enumerates the workstreams that the delivery team will execute. Each
workstream should be a coherent body of work such as Discovery and Assessment, Landing
Zone and Foundation, Migration Execution, Application Refactoring, Security and
Compliance, and Cutover and Hyivecare. For each workstream describe what is done and what
the boundary is. A scope section is incomplete without an explicit "Out of Scope" list
that protects both parties from scope creep. Typical out-of-scope items include end-user
training beyond admin enablement, ongoing managed services after hypercare, and changes to
third-party systems not named in the objectives.

## Deliverables Guidance
Deliverables are tangible artifacts handed to the client. Good deliverables are nouns, not
verbs: an Assessment Report, a Target Architecture Document, a Migration Runbook, a
Landing Zone (infrastructure as code), a Security and Compliance Matrix, and a Hypercare
Exit Report. Each deliverable should be acceptance-testable. Avoid vague deliverables like
"improved system"; instead say "Refactored order-management service deployed to
production with automated CI/CD pipeline."

## Timeline and Milestones Guidance
Break the timeline into phases that map to the workstreams. A six-month cloud engagement
typically splits into Discovery (Weeks 1-4), Foundation (Weeks 3-8), Migration Waves
(Weeks 6-20), and Cutover plus Hypercare (Weeks 20-26). Always express milestones as
verifiable events: "Landing zone accepted," "Wave 1 applications live in production,"
"Hypercare exit." When the input timeline is missing, infer a default from project type
and budget rather than leaving it blank.

## Assumptions Guidance
Assumptions document the conditions the estimate depends on. They protect the estimate
when reality differs from expectation. Standard assumptions include: the client provides
timely access to environments and SMEs, source system documentation exists, a single
production cutover window is available per wave, and the client owns third-party license
procurement. Compliance-heavy engagements add assumptions about audit evidence
availability and the client's existing control framework.

## Commercials Guidance
State the budget range, the commercial model (fixed-fee, time-and-materials, or
milestone-based), and the basis of estimate. When budget is provided as a range, anchor
the proposal to the midpoint and note which scope items are optional levers that move the
price up or down.

## Handling Unknown or Missing Client Information
When the client name is "Unknown" or missing, use a neutral placeholder such as "the
Client" and proceed; do not block generation. When objectives are vague (for example
"Improve systems"), expand them into concrete, defensible objectives appropriate to the
stated project type. A "Modernization" project with vague goals should default to
objectives around reducing technical debt, improving deployment frequency, improving
reliability, and reducing total cost of ownership.
